## Context

Week 0's raised expiry is a stopgap. This adds a real archive: a cleaned, structured copy of every parsed email, encrypted with a customer-managed key, retained indefinitely at low cost. #98 (the bucket's SSE-C encryption drift) must be reconciled first, because this changes the same bucket's encryption. Specification: PLAN.md § Week 1. Decisions: D-06.

Week 0 left two hazards for this task (see JOURNAL.md § Week 0 and PR #144):

- **Lambda code-hash drift.** The untargeted plan shows `source_code_hash` changes on both `module.lambda_api_handler` and `module.lambda_email_parser`. A bare `terraform apply` redeploys both production Lambdas from whatever `bootstrap` binaries are on the machine running it.
- **Raw bodies after 20 Nov exist only under `incoming/`.** `archive/raw/` was a one-time sync on 20 Nov, and `archive/clean/` stores cleaned JSON with no backfill of raw bodies. Lowering the expiry to 30 days without a fresh sync permanently deletes every raw body older than 30 days that arrived after the copy.

## Tasks

- [ ] New customer-managed KMS key (Terraform), scoped to the parser role and the bucket. The bucket default stays AES256 so SES delivery to `incoming/` never depends on the key (D-06)
- [ ] Every `archive/` and `evals/` write names the key explicitly (`ServerSideEncryption=aws:kms` + `SSEKMSKeyId` on `PutObject`/`CopyObject`). Add a bucket policy that denies `s3:PutObject` on `archive/*` and `evals/*` unless the request names that key
- [ ] After a successful parse, the email-parser writes `archive/clean/{messageId}.json`: cleaned body, parsed headers, `IsForwarded`, the extraction result, parser version
- [ ] The email-parser also copies the raw `.eml` to `archive/raw/{messageId}` **without tags** (`CopyObject` with `TaggingDirective=REPLACE`), so `archive/raw/` keeps every original, not only week 0's. `{messageId}` is the SES `MessageID`, the same name the object has under `incoming/`, not the `Message-ID` header. Handler order:
  1. The SES verdict check stays first.
  2. Then the raw copy, which runs **before parsing**. A failure here fails the invocation, so Lambda's async retries run it again (and the existing `email-parser-errors` alarm fires) instead of losing the only copy that can't be regenerated.
  3. Mail that failed the SPF, DKIM or spam verdict **is copied** and then stops there: it is archived, never parsed, and counts as `rejected` as today.
  4. Mail that failed the **virus** verdict is **not copied**; it expires from `incoming/` as usual.
  5. Today a per-record failure is swallowed and the invocation succeeds. Returning an error when the raw copy fails changes that; call it out in the PR.
- [ ] Grant the parser role `s3:PutObject` on `archive/*` and `kms:GenerateDataKey` on the key
- [ ] Before any untargeted `plan`/`apply`: rebuild both Lambdas from a clean checkout of `main` with `make build-lambdas`. Builds aren't byte-reproducible, so the hash may still differ; the point is that any redeploy ships `main`'s code
- [ ] Right before lowering the expiry: re-run `aws s3 sync s3://sh3r4rd-recruiter-emails/incoming/ s3://sh3r4rd-recruiter-emails/archive/raw/ --copy-props metadata-directive --sse aws:kms --sse-kms-key-id <key ARN>`, excluding virus-flagged keys (without `--sse` the copies would be AES256, and the bucket policy would reject them). Confirm with `get-object-tagging` that none of the new copies carry tags, and that the `archive/raw/` key set is a superset of `incoming/` minus virus-flagged keys. Optionally re-copy week 0's AES256 objects in place with KMS so the whole prefix uses one key
- [x] Fix the `s3_lifecycle_expiration_days` comment in `terraform.tfvars` (it cites #131; the restore belongs to this issue), then `make tf-vars-push` (done 21 Nov 2026 in PR #144)
- [ ] Lifecycle: `archive/` transitions to Intelligent-Tiering with no expiry; set `s3_lifecycle_expiration_days` back to 30 **last**, only after the parser change is deployed and the re-sync above confirms coverage
- [ ] Apply the same KMS key to the `evals/` prefix (D-06)
- [ ] Unit tests for the archive writer (table-driven, mocked S3): both failure paths below, the SSE-KMS parameters on each write, and the verdict cases (spam/SPF/DKIM fail → copied and not parsed; virus fail → not copied)
